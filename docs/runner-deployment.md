# Runner Control Plane deployment

This is the operational procedure for `.github/workflows/deploy-control-plane.yml` and `infra/main.bicep`. It describes the intended configuration, **not a verified Azure deployment**. Validate it in an isolated Azure subscription/resource group and GitHub repository before production. Image building and validation integrations remain unconfigured; automatic production promotion is not delivered here.

## Topology and limits

The template creates a dedicated Linux App Service plan, production app and staging slot, a separate worker app, a user-assigned managed identity, and a storage account. Tables store capacity, images, Runner VMs, rollouts and queued image work; a private blob stores the shared authentication key ring, encrypted using an existing Key Vault key. Both the workflow and direct Bicep deployments default to table-backed state. Set `tableStorageEnabled=false` only during a controlled migration of existing files. Apps use .NET 10, HTTPS, Always On, `P1v3` by default, and run-from-package. Outputs include `appUrl`, `stagingUrl`, `workerUrl`, `tableStorageAccountName`, and `tableStorageEndpoint`. The workflow uses the default hostname, not a custom domain. The Key Vault and optional VM Scale Set must already exist in the same subscription; the VM Scale Set is not created by this deployment.

Subsequent package releases deploy and warm the staging slot, then swap it into production without stopping the production app. `/health/ready` checks table access, incomplete migrations and the shared data-protection provider; swap warmup requires HTTP 200. Slot swapping, key access, and uninterrupted traffic must be verified in the target Azure environment; a first deployment and migration of a file-backed installation require maintenance.

The template defaults to company `mm`, product `ghshr`, environment `prod`, location code `uks`, and Azure location `uksouth`. The resulting resource prefix is `mm-ghshr-uks-prod`; the app, worker, plan, identity and existing vault names use the suffixes `app`, `worker`, `asp`, `id` and `kv`. The storage account uses a compact lowercase prefix, `st`, and a resource-group-derived hash because storage names cannot contain hyphens and must be globally unique. Override the name parameters when adopting existing resources; a changed name creates a different resource, not a rename. Keep `location` and `locationShort` consistent when changing regions. The workflow retains explicit environment-variable overrides and uses the resource group's location to preserve existing deployments.

The workflow deploys a resource-group deployment stack with `detachAll` and no deny assignments. Resources removed from its template are detached, not automatically deleted; deleting the resource group can still delete them. The deployer needs deployment stack permissions in addition to the deployment and resource permissions below. Validate stack adoption of existing and cross-resource-group role assignments in an isolated environment before production.

The production and staging web apps have `BackgroundWorkers__Enabled=false`; the separate worker app has it set to `true` and runs cleanup, capacity reconciliation, image scheduling and the build queue. It exposes only `/health/ready`. Both web slots use the same disabled setting, including during swap warmup, so staging does not process production work and a web-slot swap does not recycle the worker. Restrict access to staging as appropriate: it is still an authenticated API and can modify shared state. Do not share the plan with other apps or use extra slots. The workflow checks for other apps, unexpected slots and enabled plan autoscale in the target resource group. It uses one instance per app; do not enable autoscale without separately validating the topology. Do not overlap file-backed writers. Table-backed capacity and VM operations use fail-closed cross-instance locks, and image queue claims are durable. An interrupted or uncertain operation can require operator reconciliation before work resumes; a slot swap does not make an external build or VMSS operation transactional.

When Table Storage is disabled, `/home/runner-control-plane/runner-capacity-state.json` holds capacity settings and audit records; `/home/runner-control-plane/runner-image-state.json` holds image registrations, results and audits. The stores use same-directory temporary files and atomic replacement. Verify write access, same-filesystem atomic replacement, restart and redeployment persistence in the selected App Service SKU/region before relying on them; `/home` is not a backup. Back up these files securely with the app stopped and restore them only with all writers stopped. When Table Storage is enabled, those files are no longer updated. Deleting the app, storage account, or tables can destroy state; arrange independent backups and recovery.

In file-backed mode Runner VM and rollout records remain in memory. In table mode their records and audits survive restarts. A claimed image build is never automatically repeated after an interrupted or ambiguous operation; reconcile the external builder and image record before submitting a new build. The default builder and validator deliberately fail rather than build or validate an Azure image. VM Scale Set operations are disabled by default; the disabled implementation does not provision Azure VMs.

## Bootstrap and permissions

1. Create the target resource group and an RBAC-enabled Key Vault, and provision two enabled secrets **before** deploying: the Entra web app client-secret **value**, and the GitHub token. Provision an enabled Key Vault key supporting wrap and unwrap for data protection. The template creates neither the vault, key nor secret values. Retain old key versions when rotating the key. Allow App Service's managed identity network access to the vault. Secret and key names and vault metadata are deployment inputs; do not put values in GitHub variables, Bicep parameters, source, artifacts or logs.
2. Register a single-tenant Entra web/API app. Add the exact web redirect URIs `https://<actual-default-hostname>/signin-oidc` and `https://<actual-default-hostname>/signout-callback-oidc` for sign-in and sign-out. Configure two distinct security groups and emit their object IDs in user principals' `groups` claims for browser sign-in and user API access; group claims are not the app-only workflow authorization mechanism. Request v2 access tokens (`api.requestedAccessTokenVersion: 2`), expose the API, and set `ENTRA_API_AUDIENCE` to its v2 audience (normally the API client ID). Set `RUNNER_IMAGE_API_SCOPE` to the API's application ID URI followed by `/.default`, for example `api://<api-client-id>/.default`; this is not an Azure management scope. Configure the API resource application's optional **access token** `idtyp` claim. Grant the workload any API application permissions/consent required by the tenant and its app assignment policy so an app-only token can be issued.
3. Configure the image workload application/service principal to obtain an app-only token for that API. The deploy workflow derives its `imageWorkloadClientId` Bicep parameter from `AZURE_CLIENT_ID`, the same Azure login client ID used by the image workflow, and sets `RunnerImageBuild__WorkloadClientId` to that value; no separate `IMAGE_WORKLOAD_CLIENT_ID` variable is used. It must match the token's `azp` or `appid`. A validated token also requires `idtyp: app` and no `scp`; it gets only image registration and result callback access through this policy, not reader/operator access. User reader and operator rights depend on group claims. See [runner access](runner-access.md) for GitHub token permissions and sign-in; the token also needs Actions read for eligible private repositories and the queue-read permissions in [capacity](runner-capacity.md).
4. Configure a GitHub Actions OIDC federated credential on the Azure login application with issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`, and subject `repo:<owner>/<repository>:environment:production`. Create and protect the GitHub environment named `production`, allow only the `main` branch, and require appropriate reviewers. An environment subject does **not** encode the branch: the environment branch restriction and workflow `main` guards are both important. PRs must not access the production environment or credentials. Scheduled and manual image runs and deployment all use this same environment; a manually dispatched run must select `main`.
5. Assign the deployment principal permissions scoped to the target resources: deployment stack and resource-group deployment operations, storage account and table management, App Service plan/site/configuration and package deployment/start/stop operations, user-assigned identity creation and assignment, and the reads used to inspect apps, slots and autoscale settings. It also needs `Microsoft.Authorization/roleAssignments/write` at each table, blob container, existing secret and key scope and, when enabled, the VM Scale Set scope; nested deployments need deployment permissions in those resource groups. Use appropriately scoped custom roles or equivalent authorized roles, not subscription-wide Owner by default. Grant the principal access to read the named App Service for image discovery. Both workflows currently use the **same** `production` `AZURE_CLIENT_ID`, so this configuration does not provide a separate read-only Azure principal for image runs; protect that identity accordingly.

The template grants the app's managed identity **Key Vault Secrets User** separately at each secret, **Key Vault Crypto User** at the data-protection key, **Storage Table Data Contributor** at each table and **Storage Blob Data Contributor** at the private key-ring container. Restrict key-ring access: writers can alter authentication keys. It disables storage shared keys, uses versionless Key Vault references and `AZURE_CLIENT_ID` selects the managed identity for Azure SDK calls. Allow network access and time for role propagation. The deployer needs role-assignment authority, not secret values. With VMSS enabled, precreate a custom role covering VM Scale Set read/update, instance listing and deletion of selected instances, assignable at the existing VMSS scope; supply its full role-definition resource ID. The template assigns it to the app identity at that VMSS, not the subscription. Confirm exact Azure provider actions and least-privilege scope in the target environment before enabling it. The VMSS must bootstrap runners with the configured label and matching VM host/runner names; see [capacity](runner-capacity.md).

Its settings also set `Entra__TenantId`, `Entra__ClientId`, `Entra__ApiAudience`, `Entra__ReadOnlyGroupId`, `Entra__OperatorGroupId`, `GitHub__Organization`, `GitHub__RunnerGroupId`, `Runner__Label`, `RunnerImageBuild__WorkloadClientId`, `AzureVmScaleSet__Enabled`, `AzureVmScaleSet__SubscriptionId`, `AzureVmScaleSet__ResourceGroupName`, and `AzureVmScaleSet__ScaleSetName`. Treat the Bicep settings as authoritative on redeployment; do not rely on manual portal settings surviving it.

## Migrating file state to tables

For an existing file-backed app, the release workflow refuses to provision the slot or run until a separately approved maintenance migration has put the app in table mode. Pause all API writers, image schedules and external work; finish or reconcile local queued/building/validating images. Export authenticated JSON snapshots of `/api/runner-vms`, `/api/runner-vms/audit`, `/api/runner-images/rollouts`, and `/api/runner-images/rollouts/audit` before stopping the old app. The old process-local stores cannot provide an atomic snapshot with their background workers: verify the snapshot against Azure and GitHub and reconcile any changes or uncertain operations before continuing. Stop the app, verify all writers have stopped, and securely copy and back up both state files and snapshots.

Provision the stack, tables, worker and staging slot during the maintenance window using the workflow's stack parameters, explicitly setting `tableStorageEnabled=false`, preserving existing resource names and referencing the existing data-protection key. Do not deploy or start the worker package in file mode: it would not share the web app's files. Ensure the old application is stopped throughout import, even if an infrastructure update starts it. Use the same release's source or published executable and an Azure identity granted **Storage Table Data Contributor** on the tables. Get the HTTPS table service endpoint from the stack output or storage account. For each file that exists, run:

```bash
dotnet run --project src/RunnerControlPlane --no-launch-profile -- --import-table-state "$TABLE_ENDPOINT" capacity /secure/path/runner-capacity-state.json
dotnet run --project src/RunnerControlPlane --no-launch-profile -- --import-table-state "$TABLE_ENDPOINT" images /secure/path/runner-image-state.json
dotnet run --project src/RunnerControlPlane --no-launch-profile -- --import-table-state "$TABLE_ENDPOINT" vms /secure/path/vms.json /secure/path/vm-audit.json
dotnet run --project src/RunnerControlPlane --no-launch-profile -- --import-table-state "$TABLE_ENDPOINT" rollouts /secure/path/rollouts.json /secure/path/rollout-audit.json
```

These imports do not overwrite existing rows. A failed import may leave partial data; investigate and reconcile the affected table before retrying, rather than assuming it completed. The capacity, VM and rollout imports mark incomplete migrations as locked; image imports report possible partial writes. Verify every record, setting, and audit against the backups while writers remain stopped. Set `tableStorageEnabled=true` in the maintenance stack deployment, then deploy the tested package directly to production and the worker during the maintenance window and start them. The normal release workflow cannot perform this first upgrade: it requires the existing production package to pass `/health/ready` before swapping. Verify both readiness endpoints and authenticated API data before resuming writers, and set `TABLE_STORAGE_ENABLED=true` for subsequent releases. Missing files mean no prior state for that store; check this explicitly. Migrating to the new key ring can invalidate existing browser sessions once; subsequent slots share it. Do not switch back to files after writing to tables without exporting and reconciling table state. Table Storage limits a serialized image, VM or rollout property to 64 KiB; oversized records fail rather than being truncated.

## Deploy and operate

A push to `main` or manual dispatch on `main` validates Bicep, builds, tests and publishes a release artifact; only a successful release feeds the protected production deploy job. For a new app only, set `INITIAL_BOOTSTRAP_CONFIRMED=true` to create the stack and deploy production and the worker, then remove the variable. Existing applications must already have the managed staging slot, dedicated worker and table-backed state. Releases do not redeploy the stack, update the worker package, or change production infrastructure: separately approve and apply those changes in maintenance. The workflow checks worker configuration and readiness, deploys the tested web package to staging, waits for `/health/ready`, swaps staging into production, and checks readiness again. It attempts a reverse swap after a post-swap readiness failure. An ambiguous failed swap requires manual inspection before any retry. Requests in flight on the former production slot may be interrupted; reconcile any uncertain mutations. A scheduled/manual image workflow independently discovers the named running app via Azure metadata; it never redeploys the app or uses a manually maintained URL. See [image builds](runner-images.md).

The deploy and image jobs do not share a concurrency lock. Back up state and record the current release before deployment. Claims and operation locks intentionally fail closed after interruption; do not blindly retry external operations.

## Updating the deployment stack and worker

Ordinary web releases intentionally do not reapply the stack: even a configuration update can recycle production or the worker. Before changing infrastructure, schedule an approved maintenance window, back up tables and the key ring, record the current package and stack parameters, pause callers and schedules, and let external operations finish. Inspect capacity/VM locks and claimed builds and reconcile uncertain work before stopping or restarting a worker. Do not run this update concurrently with a release or another stack update.

Prepare a non-secret ARM parameters file containing the **complete intended values**, including the exact existing resource names, both app names, region, VMSS settings, Key Vault names, and `tableStorageEnabled=true`; use the values passed in the workflow's **Provision infrastructure** step as the starting point. Do not put secret values in it. Review the current stack resources with `az stack group show`, then preview and apply the same reviewed template and parameters:

```bash
az deployment group what-if --resource-group "$AZURE_RESOURCE_GROUP" --template-file infra/main.bicep --parameters @/secure/path/control-plane.parameters.json
az stack group create --resource-group "$AZURE_RESOURCE_GROUP" --name control-plane-production --action-on-unmanage detachAll --deny-settings-mode none --yes --template-file infra/main.bicep --parameters @/secure/path/control-plane.parameters.json
```

What-if is not a complete preview of stack detach behavior: separately compare the stack's currently managed resources with the template and verify `detachAll` is intended. Abort on unexpected replacements, resource names, role assignments or deletions. Infrastructure updates may interrupt traffic; verify production, worker and staging configuration, identity access and readiness after the update before resuming activity.

Update the worker package separately in maintenance only after ensuring the new web and worker versions are compatible with the same table schema and queue format. Drain and reconcile active work first; then deploy the tested package to `AZURE_WORKER_APP_NAME` with `az webapp deploy --type zip`, start it and verify its readiness and worker activity. A worker restart can interrupt an external operation; follow failure recovery below instead of automatically replaying a claim or clearing a lock.

## Isolated verification before production

Use an isolated subscription/resource group, Key Vault, Entra applications, test GitHub organization/Runner group, and repository with the same protected environment named `production`. Point all variables and federation subjects to those isolated resources; leave live VMSS operations disabled unless explicitly testing a disposable VMSS. Restrict access, retain only redacted evidence, and never print tokens or secret values.

1. Validate the template using `az bicep build --file infra/main.bicep --stdout` and an ARM what-if/validation with the same non-secret parameters used by the workflow. Run the stack deployment on `main`, approve the environment, and verify managed resources, both slots, tables, private blob container, identity permissions, and Key Vault references. Check the output URL against the App Service default hostname.
2. Verify unauthenticated API access returns `401`; a valid v2 user token for the configured tenant/audience with a reader group can GET but cannot modify; an operator can perform a safe isolated settings change; a valid user outside both groups receives `403`. Check browser login and logout and their exact HTTPS callbacks. Test the app-only workload token's `tid`, `aud`, `idtyp`, `azp`/`appid` and absence of `scp` without logging the token: it can register but is forbidden from group-protected reads and unrelated management. Check that a wrong workload identity, a delegated token without operator membership, or a token with wrong tenant or audience cannot register.
3. Record an image registration, safe capacity settings change, VM and rollout records and audits via the API. Restart and deploy another release; compare records and audits after each operation. Exercise a slot swap with a continuous authenticated request stream and an existing browser session, verifying no gaps and shared cookie keys. Test interrupted claims and migration failures separately and verify they fail closed.
4. Dispatch the image workflow from `main`; check the Azure-discovered target and successful authorized registration and matching digest without exposing the token. Allow a real weekly scheduled run in the isolated repository and verify the same checks; a manual dispatch alone does not test the scheduled event. Test missing/wrong app, wrong scope and denied workload identity separately and confirm registration stops. A `403` on the workload's authenticated readiness GET is expected; the POST must succeed. Registration is not image creation or promotion.
5. Stop isolated runs and the app, remove test Runner registrations and disposable VMs/VMSS, resource group and any separately scoped test role assignments, secrets and vault as appropriate. Remove test Entra apps/federated credentials, GitHub variables and environment protections when no longer needed. Preserve only approved redacted evidence and backups per retention policy; do not delete shared resources.

## Failure recovery and rotation

If staging readiness fails, production is not intentionally swapped. If a swap reports failure, its outcome may be ambiguous: inspect both slots and their deployed versions before retrying or manually swapping. If rollback fails or production remains unhealthy, restore a known tested release and verify authorization and state. Check identity propagation, storage and vault network access, key and secret availability, and application logs without printing credentials.

Capacity operations use the `runner-capacity` settings row's `Owner` as a non-expiring lock; VM and rollout operations use `runner-vm-operations/global-lock` in `RunnerVms`. If an operation is interrupted or its outcome is uncertain, stop all writers, confirm the prior process and external Azure operation have stopped, and reconcile the VMSS, VM records, rollout and audit. Only then may an authorized operator clear the specific lock using its current ETag. Never clear a migration guard to bypass a partial import; reconcile or restore the complete affected partition first. A `Claimed` row in `RunnerBuildQueue` is deliberately not replayed after interruption: reconcile the external build and image before submitting a new one, and do not reset a weekly claim.

For Entra or GitHub token rotation, create a new valid credential with equivalent limited permissions, update the corresponding existing Key Vault secret as a new version, and allow the versionless reference to refresh. If needed, use the App Service Key Vault reference refresh operation and verify both reference statuses are `Resolved` without showing values. Confirm web sign-in or GitHub group/queue access with the new credential before revoking the old one; plan for refresh or restart interruptions and never log the secret. An Entra client-secret change also requires the new credential on the app registration. On `401`, check v2 issuer, tenant and audience; on `403`, check group claims or the workload client ID and `idtyp`/`scp` claims. Check Azure resource identity and read permission if discovery fails, and vault RBAC/network/propagation if references do not resolve.
