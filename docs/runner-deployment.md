# Runner Control Plane deployment

This is the operational procedure for `.github/workflows/deploy-control-plane.yml` and `infra/main.bicep`. It describes the intended configuration, **not a verified Azure deployment**. Validate it in an isolated Azure subscription/resource group and GitHub repository before production. Image building and validation integrations are unconfigured; durable rollout history and automatic production promotion are not delivered here.

## Topology and limits

The template creates a dedicated Linux App Service plan, one App Service and a user-assigned managed identity in the target resource group. It uses .NET 10, HTTPS, Always On, `P1v3` by default, one worker, persistent App Service `/home`, and run-from-package. It outputs the non-secret `appUrl`. The workflow uses the default hostname, not a custom domain. The Key Vault and optional VM Scale Set must already exist in the same subscription; the VM Scale Set is not created by this deployment.

Only one process/worker may write the stores: their locks are process-local. Do not share the plan, use slots, enable autoscale, scale out, run another deployment against the same files, or change the settings that disable overlapped recycling. The workflow checks for other apps in the plan in the target resource group, slots and enabled plan autoscale in that resource group; prohibit autoscale elsewhere with Azure policy and restrict external deployments, scaling and slot creation. A deployment stops the app and interrupts normal operation. Expect downtime and interrupted requests, background reconciliation and in-flight work. Coordinate a maintenance window and pause image registration and other writes.

`/home/runner-control-plane/runner-capacity-state.json` holds capacity settings and audit records; `/home/runner-control-plane/runner-image-state.json` holds image registrations, results and audits. The stores use same-directory temporary files and atomic replacement. Verify write access, same-filesystem atomic replacement, restart and redeployment persistence in the selected App Service SKU/region before relying on them; `/home` is not a backup. Back up these files securely with the app stopped and restore them only with all writers stopped. Deleting the app or its storage can destroy state.

Runner VM records, VM removal audits, rollout records and rollout audits are in memory and disappear on restart/redeployment. Reconcile against Azure and GitHub before resuming operations; a persisted image record is not durable rollout history. Do not use this deployment for automatic production image promotion or assume it can resume an in-flight rollout after a restart. The default builder and validator deliberately fail rather than build or validate an Azure image. VM Scale Set operations are disabled by default; the disabled implementation does not provision Azure VMs.

## Bootstrap and permissions

1. Create the target resource group and an RBAC-enabled Key Vault, and provision two enabled secrets **before** deploying: the Entra web app client-secret **value**, and the GitHub token. The template creates neither the vault nor secret values. Allow App Service's managed identity network access to the vault. Secret names and vault metadata are deployment inputs; do not put values in GitHub variables, Bicep parameters, source, artifacts or logs.
2. Register a single-tenant Entra web/API app. Add the exact web redirect URIs `https://<actual-default-hostname>/signin-oidc` and `https://<actual-default-hostname>/signout-callback-oidc` for sign-in and sign-out. Configure two distinct security groups and emit their object IDs in user principals' `groups` claims for browser sign-in and user API access; group claims are not the app-only workflow authorization mechanism. Request v2 access tokens (`api.requestedAccessTokenVersion: 2`), expose the API, and set `ENTRA_API_AUDIENCE` to its v2 audience (normally the API client ID). Set `RUNNER_IMAGE_API_SCOPE` to the API's application ID URI followed by `/.default`, for example `api://<api-client-id>/.default`; this is not an Azure management scope. Configure the API resource application's optional **access token** `idtyp` claim. Grant the workload any API application permissions/consent required by the tenant and its app assignment policy so an app-only token can be issued.
3. Configure the image workload application/service principal to obtain an app-only token for that API. The deploy workflow derives its `imageWorkloadClientId` Bicep parameter from `AZURE_CLIENT_ID`, the same Azure login client ID used by the image workflow, and sets `RunnerImageBuild__WorkloadClientId` to that value; no separate `IMAGE_WORKLOAD_CLIENT_ID` variable is used. It must match the token's `azp` or `appid`. A validated token also requires `idtyp: app` and no `scp`; it gets only image registration and result callback access through this policy, not reader/operator access. User reader and operator rights depend on group claims. See [runner access](runner-access.md) for GitHub token permissions and sign-in; the token also needs Actions read for eligible private repositories and the queue-read permissions in [capacity](runner-capacity.md).
4. Configure a GitHub Actions OIDC federated credential on the Azure login application with issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`, and subject `repo:<owner>/<repository>:environment:production`. Create and protect the GitHub environment named `production`, allow only the `main` branch, and require appropriate reviewers. An environment subject does **not** encode the branch: the environment branch restriction and workflow `main` guards are both important. PRs must not access the production environment or credentials. Scheduled and manual image runs and deployment all use this same environment; a manually dispatched run must select `main`.
5. Assign the deployment principal permissions scoped to the target resources: resource-group deployment operations, App Service plan/site/configuration and package deployment/start/stop operations, user-assigned identity creation and assignment, and the reads used to inspect apps, slots and autoscale settings. It also needs `Microsoft.Authorization/roleAssignments/write` at each existing secret scope and, when enabled, the VM Scale Set scope; nested deployments need deployment permissions in those resource groups. Use appropriately scoped custom roles or equivalent authorized roles, not subscription-wide Owner by default. Grant the principal access to read the named App Service for image discovery. Both workflows currently use the **same** `production` `AZURE_CLIENT_ID`, so this configuration does not provide a separate read-only Azure principal for image runs; protect that identity accordingly.

The template grants the app's managed identity **Key Vault Secrets User** separately at each secret scope; it uses versionless Key Vault references and `AZURE_CLIENT_ID` selects that identity for Azure SDK calls. The deployer needs role-assignment authority, not secret values. With VMSS enabled, precreate a custom role covering VM Scale Set read/update, instance listing and deletion of selected instances, assignable at the existing VMSS scope; supply its full role-definition resource ID. The template assigns it to the app identity at that VMSS, not the subscription. Confirm exact Azure provider actions and least-privilege scope in the target environment before enabling it. The VMSS must bootstrap runners with the configured label and matching VM host/runner names; see [capacity](runner-capacity.md).

Its settings also set `Entra__TenantId`, `Entra__ClientId`, `Entra__ApiAudience`, `Entra__ReadOnlyGroupId`, `Entra__OperatorGroupId`, `GitHub__Organization`, `GitHub__RunnerGroupId`, `Runner__Label`, `RunnerImageBuild__WorkloadClientId`, `AzureVmScaleSet__Enabled`, `AzureVmScaleSet__SubscriptionId`, `AzureVmScaleSet__ResourceGroupName`, and `AzureVmScaleSet__ScaleSetName`. Treat the Bicep settings as authoritative on redeployment; do not rely on manual portal settings surviving it.

## Deploy and operate

A push to `main` or manual dispatch on `main` validates Bicep, builds, tests and publishes a release artifact; only a successful release feeds the protected production deploy job. The deploy job serializes production deployments, validates topology, stops the app, deploys Bicep with `sleep infinity` as a maintenance startup command, stops the app again and waits for both Key Vault references to resolve. It starts maintenance mode, synchronously deploys the tested package without a restart or deployment-status tracking, stops maintenance, clears `appCommandLine` via an ARM REST PATCH, verifies it is empty, and starts the app. It then expects an unauthenticated `401` from `/api/runner-images`. This maintenance/Kudu sequence, Linux recycle behavior and atomic replacement require isolated Azure verification. In particular, `sleep infinity` does not answer HTTP startup probes and the maintenance container may be recycled before or during package deployment; reliability is not established. The `401` is only a basic HTTPS/authentication readiness check, not proof of working user or workload authorization. A scheduled/manual image workflow independently discovers the named running app via Azure metadata; it never redeploys the app or uses a manually maintained URL. See [image builds](runner-images.md).

The deploy and image jobs do not share a concurrency lock. Pause scheduled/manual image runs and operator changes around deployment. Back up state, record the current release and reconcile any active rollout or Runner VM activity before stopping; there is no durable in-flight rollout recovery. Never run multiple replicas to avoid interruption.

## Isolated verification before production

Use an isolated subscription/resource group, Key Vault, Entra applications, test GitHub organization/Runner group, and repository with the same protected environment named `production`. Point all variables and federation subjects to those isolated resources; leave live VMSS operations disabled unless explicitly testing a disposable VMSS. Restrict access, retain only redacted evidence, and never print tokens or secret values.

1. Validate the template using `az bicep build --file infra/main.bicep --stdout` and an ARM what-if/validation with the same non-secret parameters used by the workflow. Run the deployment on `main`, approve the environment, and verify the site is running, both Key Vault references are resolved, `/home` is writable and replacement of a file in the same directory is atomic in that environment. Check the output URL against the App Service default hostname.
2. Verify unauthenticated API access returns `401`; a valid v2 user token for the configured tenant/audience with a reader group can GET but cannot modify; an operator can perform a safe isolated settings change; a valid user outside both groups receives `403`. Check browser login and logout and their exact HTTPS callbacks. Test the app-only workload token's `tid`, `aud`, `idtyp`, `azp`/`appid` and absence of `scp` without logging the token: it can register but is forbidden from group-protected reads and unrelated management. Check that a wrong workload identity, a delegated token without operator membership, or a token with wrong tenant or audience cannot register.
3. Record an image registration and a safe capacity settings change and audit via the API. Restart the app, then redeploy the same revision through the workflow, and compare the image record, settings and audit via authenticated GETs after each operation. Verify separately that in-memory VM/rollout records are lost and reconcile any associated external resources. Repeat deployment to check it does not reset persistent data; verify there was no overlapping writer.
4. Dispatch the image workflow from `main`; check the Azure-discovered target and successful authorized registration and matching digest without exposing the token. Allow a real weekly scheduled run in the isolated repository and verify the same checks; a manual dispatch alone does not test the scheduled event. Test missing/wrong app, wrong scope and denied workload identity separately and confirm registration stops. A `403` on the workload's authenticated readiness GET is expected; the POST must succeed. Registration is not image creation or promotion.
5. Stop isolated runs and the app, remove test Runner registrations and disposable VMs/VMSS, resource group and any separately scoped test role assignments, secrets and vault as appropriate. Remove test Entra apps/federated credentials, GitHub variables and environment protections when no longer needed. Preserve only approved redacted evidence and backups per retention policy; do not delete shared resources.

## Failure recovery and rotation

If provisioning, secret resolution or package deployment fails after the stop step, the app may remain stopped or running the `sleep infinity` maintenance command. Keep writers paused, inspect the failed stage, startup command and App Service diagnostics without printing credentials, correct identity RBAC propagation, vault network access, secret availability or configuration, and rerun the approved deployment on `main`. Do not simply start the app assuming the correct package and startup command are in place. If manually clearing the command, use the workflow's ARM REST PATCH and verify `appCommandLine` is empty before starting; `az webapp config set --startup-file ''` can silently ignore the empty value. If a start or readiness check fails, inspect state and logs, restore a known tested package/configuration as appropriate and verify authorization and persistent state before resuming. Do not delete state files to bypass errors; stop all writers and restore a verified backup after investigating corruption. Reconcile external VMs, runners and any interrupted rollout manually.

For Entra or GitHub token rotation, create a new valid credential with equivalent limited permissions, update the corresponding existing Key Vault secret as a new version, and allow the versionless reference to refresh. If needed, use the App Service Key Vault reference refresh operation and verify both reference statuses are `Resolved` without showing values. Confirm web sign-in or GitHub group/queue access with the new credential before revoking the old one; plan for refresh or restart interruptions and never log the secret. An Entra client-secret change also requires the new credential on the app registration. On `401`, check v2 issuer, tenant and audience; on `403`, check group claims or the workload client ID and `idtyp`/`scp` claims. Check Azure resource identity and read permission if discovery fails, and vault RBAC/network/propagation if references do not resolve.
